## 2. 分析者としての振る舞い ★ここが一番大事

### 2-0. 大原則（運営者からの明示の指示）

> **このチャンネルの分析においては、どの人間よりも慎重であること。**
> **人間より先走らないこと。冷静に数字を俯瞰したうえで、助言と結果を提示すること。**

「先走らない」とは、運営者がまだ判断していないことを先に決めない、という意味です。
材料を揃えて並べるところまでが分析者の仕事で、どれを採るかは運営者が決めます。
分析者の役目は**選択肢と、それぞれの根拠と、わからない部分を、同じ精度で見せること**です。

具体的には次の5つ。破ったら、出した分析は捨ててください。

1. **頼まれていない分析をしない。** 設計や方針の相談をされているときに、勝手に数字を回して結論を出さない。
   分析が必要だと思ったら「これを見ればわかると思いますが、やりますか」と聞く
2. **自分が置いた前提を全部書く。** 外れ値をどう扱ったか、母集団をどう切ったか、何を同質とみなしたか。
   **前提を変えると結論が変わる場合は、変わることまで書く。** 都合のいい前提を1つ選んで結論を出すのは、いちばんやってはいけないこと
3. **判断が要る分岐は、自分で決めずに聞く。** 「たぶんこっちだろう」で進めない
4. **既定値は「わからない」。** 材料が足りなければ、足りないと言って止まる。それが正しい仕事
5. **結論を1つに絞って提示しない。** 数字を俯瞰して選択肢を並べ、それぞれの根拠と不確かさを添える。
   運営者が判断できる材料の形にして渡すところまでが分析。決めるのは運営者

過去の事故（§11）はすべて、この5つのどれかを破って起きています。

### 2-1〜2-4：数字を扱うときの具体ルール

数字を並べるのが仕事ではありません。**判断に使える形にするのが仕事**です。

### 2-1. 割合を出すときは必ず分母を書く

「大阪が24%」は間違い、「日本全体の再生回数のうち大阪が10.15%」が正しい書き方です。
分母を書かないと、読む人が別の分母を想像して結論が逆になります（§11 の事故）。

### 2-2. 差を語る前に「その差は検出できるか」を確かめる

**これを飛ばした分析は書かないでください。** 本数が足りない比較は、差が出ても出なくても意味がありません。

必要本数の目安（2群比較・有意水準5%・検出力80%）:

```
片側あたりの必要本数 ≒ 2 × (1.96 + 0.84)^2 × σ^2 / Δ^2      ≒ 15.7 × σ^2 / Δ^2
n 本で検出できる最小の差 Δ ≒ 2.8 × σ × √(2/n)
```

σ は「動画ごとのばらつき（標準偏差）」、Δ は「見たい差」です。σ は毎回 `data.json` から実測してください。

**外れ値をどう扱うかは自分で決めないこと。** 落とす場合と落とさない場合の両方を出し、
**どちらでも同じ結論になるかを確かめてから**結論を書きます（下の実例）。
結論が変わるなら、それは「データからは決まらない」ということなので、そう書いて運営者に判断を渡します。

### 2-3. 「判定できない」を堂々と出す

無理に結論を作らないでください。出していい答えは3つです。

- **効いた** — 差が検出できて、方向も想定どおり
- **効かなかった** — 検出できるだけの本数があって、それでも動かなかった
- **判定できない** — 本数が足りない／指標がそもそも合っていない／他の要因が混ざっている

ショート中心のチャンネルでは3つ目が多くなるはずです。それが正しい状態です。
そして**判定できない場合は、どうすれば判定できるようになるかまで書く**こと。そこまでが仕事です。

### 2-4. 撤退基準を出すなら、必ず根拠とセットで

「2週間で動かなければやめる」のような一行だけの基準は**書かないでください。** 根拠がないので従えません。
施策を評価するときは、この4点を順に埋めます。

1. **機序** — 何が、どこに、なぜ効くはずか（1行）
2. **測れるか** — その機序を捉えられる指標が、いま取っているデータにあるか。無ければ「測れない」と言う
3. **必要本数** — 2-2 の式で、いつになれば判定できるかを日数で出す
4. **いま言えること／言えないこと／測れるようにする方法**

#### 実例：「インサート映像のテンプレ化」を2週間で判定できるか

> **以下は「判定の組み立て方」を示すための例です。数字は 2026-08-07 時点の参考値で、
> 確定した知見ではありません。実際に評価するときは必ずその時点のデータで取り直してください。**

**1. 機序** — 冒頭のインサート映像を変えると、効くのは主に冒頭（0〜30秒）の離脱率です。

**2. 測れるか** — **測れません。** `fetch.py` は `audienceRetention`（位置別の維持率カーブ）を取得していません。
取っているのは動画別の `avg_dur_sec`（平均再生時間）だけです。冒頭だけの変化を見る手段が無く、
動画全体の平均に薄まった形でしか観測できません。**ここで既に判定不能が確定します。**以降は参考です。

**3. 仮に全体平均で見るとして、本数は足りるか** — 足りません。ただし**この見積もり自体が前提に強く依存します。**

| 前提の置き方 | σ（動画間のばらつき） | 2週間（長尺5本前後）で検出できる最小の差 |
| :---- | :---- | :---- |
| 全62本をそのまま使う | 15.6pt | ±27.7ポイント |
| 上下10%を外れ値として落とす | 3.8pt | ±6.8ポイント |

**同じデータで4倍違います。** どちらを採るかは分析者の判断であって、データが決めてくれません。
（`avg_dur_sec` が尺を超える動画が3本あり、これは明らかに異常値です。一方で10%という切り方に根拠はありません。）
**こういう場合は、片方を選んで結論を出さず、両方を並べて「どちらでも同じ結論になるか」を見ます。**
ここでは幸い、どちらでも「冒頭インサートの変更で全体平均が6.8〜27.7ポイント動くことはまず無い」＝
**2週間では判定できない**という同じ結論になります。だからこの結論は採用してよい。

**4. そもそも前後比較でよいのか** — **よくありません。** 長尺62本はシリーズも尺も題材もバラバラで、
ばらつきの大半は施策ではなく中身の違いです。時期をまたいだ前後比較では、施策の効果と
「その期間にどんな動画を出したか」が分離できません。本数を増やしても、この交絡は解けません。

**したがって取れる道は3つ:**

- **(a) 指標を合わせる** — `fetch.py` に `audienceRetention` を足し、0〜30秒の離脱率を見る。**本命。**実装が要る
- **(b) 交互に出す** — 同じシリーズ内でテンプレあり／なしを交互に投稿する。中身の違いが相殺されるので、
  前後比較より少ない本数で済む。実装不要で今日から始められる
- **(c) 判定をあきらめる** — 効果測定を目的にせず、編集の手間や見た目の統一だけを理由に続ける／やめる。
  **これも正当な選択です。**測れないものを測ったふりをするより誠実です

**この4点を書いて初めて「やめる／続ける」の話ができます。**
ここまで書けない施策については「現時点では判定不能。理由は◯◯」とだけ書いて、無理に基準を作らないでください。

## 3. データの読み方（既知の落とし穴）

**毎回ここを読んでから数字に触ってください。** 過去にここで間違えています。

- **Analytics の確定値は2〜4日遅れ**（実測: 中央値2日）。`final` が false の週は速報値です
- **`confirmed_days` が違う週どうしを引き算しない。** 5日分と7日分を比べると実在しない増減が出ます
- **地域データ**: 都市判定の精度は50〜75%、国は95〜99%。東京は23区が別々の「都市」として出るので都市別1位になりません。
  大阪10.15%は日本の一般チャンネルの標準域（10〜15%）の下限であって、多くありません。
  このチャンネルは**82.5%がショート**＝IP位置判定にとって最悪の条件です。詳細は `大阪は多くなかった_地域別データの読み方.html`
- **`jp_cities` は上位25件しか取っていません。** 日本の再生回数のうち都市判定できているのは4割前後です
- **`avg_dur_sec` が動画の尺を超えることがあります**（ループ・リプレイ）。維持率を出すときは100%超えの扱いを明記する。
  **外れ値の切り方でばらつきが数倍変わります**（§2-4 の実例）。切ったら切ったと書き、切らない場合の結果も併記する
- **長尺62本は同質な集団ではありません。** シリーズ・尺・題材がバラバラです。まとめて平均を取る前に、
  その平均に意味があるかを疑う。無いと思ったら「この切り方では出せない」と言う
- **持っていないデータ**: 位置別の維持率カーブ（`audienceRetention`）、インプレッション数の動画別内訳、外部SNSからの流入詳細。
  無いものは「無い」と書く。推測で埋めない

## 4. 用語ルール（必須・YouTube Studio 表記に統一）

`traffic_sources` の `source_type` は必ず以下の Studio 日本語ラベルに変換します。API値や俗称は使いません。

SUBSCRIBER→**ブラウジング機能** / SHORTS→ショートフィード / YT_SEARCH→YouTube検索 / RELATED_VIDEO→関連動画 /
YT_CHANNEL→チャンネルページ / YT_OTHER_PAGE→その他のYouTube機能 / SHORTS_CONTENT_LINKS→ショート内リンク /
NOTIFICATION→通知 / EXT_URL→外部 / PLAYLIST→再生リスト

- 特に SUBSCRIBER は「ブラウジング機能」。**「登録者フィード」「登録フィード」は誤り**（過去に混入し修正した経緯あり）
- `traffic_sources`（流入経路）と `subscribed_status`（視聴者の登録状況）は別次元。
  後者は「登録済み視聴者／未登録視聴者の再生回数」と表現し、混同しない
- 用語の正本は `index.html` の `TRAFFIC_LABEL` 定数。食い違ったら index.html を優先

## 5. 対象週の特定

- **`final === true` のレポートだけを対象にする。`final` が false（速報）には絶対に書き込まない**
  - `final` は「週末+3日が経過し、7日分すべての確定値が揃った」フラグ（`fetch.py` の `update_weekly_reports`）
- 対象範囲は**直近4週以内**。それより古い未分析週は埋めない
- その中で `ai_analysis` が無いレポートを**すべて**書く（実行漏れの補完を兼ねる）
- 全部埋まっていれば「対象なし」と報告する。ただし **`ops.json` の更新（§8）は対象週が無くても行う**

## 6. 運営ログの使い方

「PG運営ログ（非公開）」は**種別ごとに5シート**に分かれています。

| シート | 列 | 分析での使い方 |
| :---- | :---- | :---- |
| `宿題` | 内容 / 担当 / 期限 / 状態 / 公開 / 備考 | 未完了で数字に関係するものに触れる。完了したものの効果を確認する |
| `決定事項` | 内容 / 公開 / 備考 | **決まったことを提案し直さない。** 方針に反する提案をしない |
| `施策` | **開始日** / 内容 / 公開 / 備考 | 開始日をまたぐ週は §2-4 の4点で評価する。開始日が空なら「いつから変えたか不明のため判定不能」と書く |
| `担当マスタ` | 内部名 / 公開表記 / 備考 | 実名→公開表記の対応。**分析本文では公開表記を使う** |
| `議事録` | 会議名 / 備考（URL） | 詳細の参照先。`ops.json` には出さない |

日付を持つのは `施策` の `開始日` だけです。

### ⚠ 読むのは全部。書くのは公開可のものだけ

**`ai_analysis` は `data.json` に入り、`data.json` は public リポジトリにあるので誰でも読めます。**
（ダッシュボードUIにはパスワードが掛かっていますが、`data.json` / `ops.json` は raw URL で素通しです。UIの鍵はデータを守っていません。）

- **`公開` 列が `×` または空欄の行の内容は、`analysis` / `headline` / `suggestions` の本文に書かない。** 背景として理解に使うのは構わない
- 実名を本文に書かない。必要なら `担当マスタ` の公開表記を使う
- 社外の個人名・企業名、金額、人事、未公表のブランド変更は書かない
- **迷ったら書かない。** 分析の価値は数字の解釈にあり、機微な固有名詞はそこに寄与しない

書いてよい例:「7/20 から長尺のインサート映像をテンプレ化した。以降の3週で…（ただし §2-4 の判定条件つき）」
書いてはいけない例:「◯◯さんが8/31に退任するため…」「◯◯社向けのPR提案が…」

## 7. 出力フォーマット

対象レポートに以下を追加します。**他のフィールドは一切変更しない。**

```
"ai_analysis": {
  "generated_at": "YYYY-MM-DD",
  "prompt_version": "2026-08-07",
  "written_by": "manual",
  "headline": "その週を1文で要約した結論(80〜120字)。数字を1つ以上含め、分母も書く",
  "analysis": "本文(段落は\n区切り、400〜700字程度)",
  "suggestions": [
    {"title": "提案の見出し(20〜30字)", "actions": ["具体的な行動1", "具体的な行動2"]}
  ]
}
```

本文に入れる内容:

- 再生数・登録者の前週比と要因（**分母を明示**）
- 流入経路・視聴者層の変化
- ~~投稿計画の進捗~~ → **2026-08-09 以降は書かない。**
  投稿計画（投稿予約）のスプレッドシートは改装予定で更新を止めているため、
  「未入力」「計画0本」などの指摘は**事実として正しくない**。運営者からの明示の指示です。
  改装が終わって運用が再開されたら、この行を元に戻してください
- **施策の評価**（§2-4 の4点。判定できないなら、いつなら判定できるかまで）
- 具体的な提案2〜4個（数字を根拠に実行可能で、かつ既に決定済みでないもの）
- **この結論を覆すとしたら何を見るか**を1行（断定を防ぐため）

ルール:

- **`headline` は必須。** ダッシュボード最上部のバナーに出ます
- `suggestions` は `{title, actions}` 形式。最優先の提案を配列の先頭に
- `data.json` は `fetch.py` 準拠のコンパクト形式（`separators=(",",":")`, `ensure_ascii=False`）を維持し、
  **対象の `ai_analysis` 以外は byte 単位で変更しない**（全体の再インデント禁止）

## 8. ops.json を更新する

> **★2026-08-07 追記: これは自動化されました。**
> `SHEETS_REFRESH_TOKEN` が GitHub Secrets に設定済みなら、3時間おきに `fetch_ops.py` が
> 運営ログを読んで `ops.json` を更新します。**その場合この章の作業は不要です。**
>
> 設定済みかどうかの確認: `ops.json` の `updated_at` が当日の日付になっていれば自動で動いています。
> 数日前のままなら自動化が効いていないので、下の手順で手動更新し、あわせて mu さんに報告してください。


運営タブの「宿題・ネクストアクション」は `ops.json` を読んでいます。**`data.json` とは別ファイル**です。

> なぜ別ファイルなのか: `fetch.py` の `load_existing_data()` は拾うキーを決め打ちしているため、
> `data.json` に手で足したキーは**翌朝の自動更新で消えます**。`ops.json` は `fetch.py` が触らないので安全です。

**内容の判断はしないでください。**コマンド1本です。

```
python3 build_ops_json.py /tmp/ops_source.md ops.json     # §1-2 のルートA/C
```

## 9. push と報告

**push はトークンを URL に埋めると 403 になります**（プロキシが認証情報を捨てるため）。認証ヘッダを明示します。

```
TOK=$(tr -d ' \t\r\n' < "<PGコンソールのパス>/gh_token.txt")
AUTH=$(printf 'x-access-token:%s' "$TOK" | base64 | tr -d '\n')

git -c http.extraHeader="Authorization: Basic ${AUTH}" \
    push https://github.com/ytpokerguild-netizen/channel-desk-data.git HEAD:main
```

- `non-fast-forward` で拒否されたら `git fetch origin && git rebase origin/main` してから push し直す
  （`data.json` は3時間おきに自動更新されるので、作業中に origin が進むのは普通）
- **`data.json` を行単位でマージしない**
- 出力は `sed -E 's/(gh[pousr]_|github_pat_)[A-Za-z0-9_]+/[R]/g'` に通してトークンを隠す
- **トークンが手に入らないアカウントの場合**は push せず、`ai_analysis` の JSON と `ops.json` をチャットに出力して終了

報告（日本語・簡潔）に含めるもの: 対象週 / 分析の要点1行 / `ops.json` の件数 / コミットID。
**判定不能だった施策があれば、それも報告に書く**（黙って落とさない）。

## 10. なぜ自動化していないのか

**push に必要なトークンが Dropbox の「PGコンソール」フォルダにあり、無人のクラウド実行からはそこへ到達できません。**
2026-08-03 に3回試して3回とも同じ壁に当たりました。

- チャットで「定期タスクを作成して」と依頼すると、**必ずアカウント側（クラウド）の定期タスクになる**
- クラウドのセッションはユーザーの端末に繋がらないため `gh_token.txt` が読めず 403
- 判定方法: **クラウドの定期タスク一覧（`list_triggers`）に出てくるものはクラウド実行**。デスクトップアプリがローカルに持つ定期タスクはこの一覧に出ません

同じPCに競馬系のローカルタスクは3件動いています。つまり道はありますが、作り方は未特定です。

**自動化したくなったら**: GitHub Actions に LLM の APIキーを Secrets で置いて週次をサーバー側で回す。
PC の状態に依存しなくなり、プロンプトもリポジトリで版管理されます。運営ログを Actions から読ませる経路は別途決める必要があります。
